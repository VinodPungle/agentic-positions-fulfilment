The short version

Scope, stated up front

This tool runs the internal fitment process — our own panel vetting a candidate before their profile ever reaches the client. It stops at the moment we decide a candidate is presentable. Sharing the profile with the client and scheduling the client-side interview are deliberately manual, outside this tool — that relationship stays with the account team.

Today, getting a candidate through internal fitment runs through a spreadsheet and a dozen Slack threads: someone reads every CV by hand, someone else remembers who's free to interview, someone chases the interviewer for feedback, and everyone finds out the status by asking. The prototype replaces the coordination labor around that work — not the judgment calls — with six purpose-built agents that hand a candidate to each other automatically and leave a single, always-current status any PM or Service Line Leader can check in seconds.

What this is not

It doesn't decide who's presentable to the client. A person still ranks the final shortlist decision, still runs the actual interview, still makes the internal-fit call, still owns the relationship with the candidate and the client. The agents remove the busywork around those decisions — reading every CV cold, tracking who's free, remembering to follow up, compiling what was discussed — so the time a PM spends is spent on the decision itself, not the legwork to get there.

How a candidate moves through internal fitment

Every open position — tracked internally as a Staff Request, ticket prefix SR- (e.g. SR-102) — is a single record that moves through a fixed set of stages. Each arrow below is a handoff that used to require someone to notice, remember, and manually tell the next person — now it fires by itself the moment the previous step finishes. The last box is the handoff out of this tool.

The two places a human is required to act

Shortlist approval: the project's PM (or the Service Line Leader, as an override) reviews the AI's ranked shortlist and reasoning before anyone gets invited to interview. Fitment decision: after the internal interview and its transcript summary come back, that same PM decides whether the candidate is Internal Fit — ready for the client — or not. Every other arrow on this diagram fires on its own. Both gates surface together on one Approvals page, scoped to the PM's own projects — one place to check, not two. What happens after Internal Fit — sharing the profile, scheduling the client interview — is a deliberate handoff to a manual process this tool doesn't touch.

The six agents

Each agent owns one narrow job end-to-end and nothing else — this is deliberate, not incidental: a scheduling bug can't corrupt an evaluation, and a Slack outage can't block an interview from being booked.

How they talk to each other — A2AWhat "agent-to-agent" means in this system

Each agent publishes a machine-readable agent card — its name, its exact skills, and the shape of the task it accepts — the same way a job description tells a new hire what they're responsible for. When one agent finishes, it doesn't ping a person to start the next step: it writes a task envelope the next agent picks up automatically. Every task carries an idempotency key, so if anything retries — a flaky network, a duplicate click — the system recognizes "I already did this" instead of double-booking an interview or double-sending a notification.

In this prototype all six run as one coordinated service sharing one datastore — that's a deliberate build choice for a fast, demoable prototype, not a limitation of the design. Because every agent already speaks the A2A contract, any of them can be pulled out into its own independently-scaled service later — e.g. if evaluation volume grows — without changing how the others talk to it.

01Always on

Orchestrator

The conductor. Owns every position's current status and the PM-approval gate. Also the one you talk to directly — ask it "what's the status of a ticket" or "how many open roles do we have" and it answers from live data, scoped to what you're allowed to see.

02On upload

Evaluation Agent

Reads the JD and every candidate CV, ranks the full pool, and writes out its reasoning per candidate — strengths, gaps, why it ranked them where it did. Re-running on an unchanged JD/CV set reuses the prior result instead of re-spending the work.

03On approval

Scheduling Agent

Matches each approved candidate to the best-available interviewer by skill overlap and current interview load — not just "who's free," but "who's the right fit and isn't already overloaded" — and sends the invite.

04Continuous

Monitoring Agent

Watches every open invite against its SLA and nudges the interviewer automatically if it's breached — no one has to remember to chase. Once feedback lands, it summarizes the interview transcript and routes it straight to the interviewer and the project's PM — the exact input the PM needs to decide Internal Fit or not.

05On demand

Reporting Agent

Compiles a fulfilment summary scoped to whoever's asking — a PM gets their project, a Service Line Leader gets the whole account with a per-project breakdown. The Staffing lead uses its chat interface directly to ask which candidates just came out Internal Fit or Rejected, rather than waiting on a PM to say so. A byproduct of the live status data, not the main event.

The point is knowing, not reporting

It's tempting to sell this on the reports it can generate. That undersells it. The actual shift is that status stops being something you have to produce and becomes something that's simply always true and always visible.

Status today
  • Lives in whoever last updated the sheet's head
  • Stale the moment something changes in Slack instead
  • Getting an answer means asking a person and waiting
Status in the prototype
  • One board, every position, always current
  • A status badge changes the instant an agent acts — nothing to sync
  • Getting an answer means typing a question and reading the reply
In the live demo

Open the Orchestrator chat and ask it something real — "how many open positions for Project Spotlight" or "what's blocked on approval right now." It answers from the same live data as the board, scoped to whoever's asking. That's the feature worth watching, more than any report it can print.

Where this stands today

This is a working prototype, demoable end-to-end on real data — not a mockup and not production. Being direct about the difference — and about what's a temporary stand-in versus a permanent scope boundary:

Already realStill a stand-in
CV/JD parsing, AI ranking, interviewer matching, SLA tracking, both decision gates, role-scoped access, the full audit trailCalendar invites & interview transcripts are mocked, not pulled from real Google Workspace
Slack notifications, if a workspace is connectedEmail is logged to an internal outbox rather than actually sent
Not a gap to close — a boundary the tool deliberately doesn't cross
Everything through the Internal Fit decisionSharing the profile with the client, scheduling the client interview, and updating Globant's Staffing Portal to reserve/release the candidate — all stay with people, by design

None of the stand-ins are architectural — they're adapters behind a fixed interface, built to be swapped for the real Google Workspace connection without touching any agent's logic.
